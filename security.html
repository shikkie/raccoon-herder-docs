Security

A den is a coding agent with a workspace. Treat it like a powerful user, not a kiosk. This page is the current product — not a phase checklist.

Token and cookies

RACCOON_TOKEN is the sole UI/API secret for that process.

  • Loopback may omit it on a host install.
  • A den fails closed if it is missing.
  • Off-loopback: Authorization: Bearer, or GET /?token= once → HttpOnly RACCOON_SESSION cookie. Scripts keep using Bearer.
  • Bad-token bursts get 429. After a den rebuild or a reused den name, close leftover tabs on that hostname first; their dead cookies count as misses and can rate-limit the next Open URL for about a minute.
  • Pairing (/pair) is for LAN from loopback. Off in dens unless --allow-pair. Do not put /pair on the public internet.

Inbound ACL

Loopback + discovered RFC1918 same-subnet + acl.allow_cidrs. acl.trusted_proxies is the only source of X-Forwarded-For. Spoofed headers from anyone else are ignored. Never trust 0.0.0.0/0.

Published Docker ports look like the bridge gateway (often 192.168.x, not only 172.16/12). Herder dens stamp 10/8,172.16/12,192.168/16. /api/health and /api/ready are unauthenticated but still go through the inbound ACL: loopback and allowed hops (acl.allow_cidrs, discovered LAN) may probe; everyone else gets 403. Herder wait_ready and kube probes come from those allowed hops.

What never goes in a den

  • docker.sock / engine sockets / kubeconfig
  • privileged, host network, host PID
  • The Herder control plane (dens must not reach it)
  • A user table or biller directory (that stays in the orchestrator)

--host-volume and --insecure-bind are operator-only.

Secret files (Herder never sees the contents)

A .env, Grok login blob, or similar file is encrypted in the browser before it is stored. Herder keeps only an AES-256-GCM envelope (salt, nonce, ciphertext). There is no password hash to compare: a mistyped passphrase fails because GCM’s authentication tag does not verify under the wrong key. That check runs in the tab (or later inside the den), not on the control plane.

Spawn and rebuild mint a one-time ticket plus a separate wrap passphrase. The ticket is only a bearer for GET /secret-once. The wrap decrypts inside the den installer and is not stored next to the ticket. Den $HOME is tmpfs, so a rebuild without a new inject leaves the dest empty — that is the point.

Edit is the same unwrap/wrap in the browser: decrypt, change the text, re-encrypt, PUT a new envelope. Herder still never sees .env bytes.

Egress: containment you can climb

Egress is the one thing an agent can do that touches the outside world, so it is worth getting graded. Raccoon Herder makes the tradeoff explicit as a paranoia ladder — every rung is operator-set, never a den/tenant toggle, and every lock* rung is fail-closed: traffic that is not explicitly allowed is dropped. The den network is per-den and isolated on every runtime.

flowchart LR
  open[open] --> lock[lock]
  lock --> audit[lock-audit]
  audit --> inspect[lock-inspect]
  inspect --> capture[lock-capture]
Rung What it does What it buys you
open Normal container DNS/egress (still no engine socket). Nothing extra. For throwaway dens on a box you control.
lock Fail-closed allowlist + per-den DNS. IPv6 metadata blocked. The den can only reach destinations you allow. Default posture.
lock-audit Forced proxy; domain-level logs. Proof of where the den talked, without breaking TLS. Recommended when you want to see egress.
lock-inspect Same proxy plus TLS termination with a Herder CA. DLP hooks; method/path and redacted body summaries. Visibility into the connection for compliance. Not a SaaS default. Breaks certificate pinning and some mTLS clients.
lock-capture lock-inspect plus a bounded, redacted capture sink: one JSON envelope per exchange, with rotation and retention. Post-incident forensics: review what actually left the den. Raw request/response bodies only with an explicit operator opt-in.

The den trusts RACCOON_INSPECT_CA only when an inspect/capture rung is stamped; lock and lock-audit never mount a custom CA. Hostname-only logs (lock-audit) are the usual choice when you just want to see destinations. Each CONNECT row includes the port (usually 443). A den can skip stolen DNS with curl --resolve host:443:ip; lock still drops that TCP, and lock-audit still logs the hostname and port.

Two honest caveats, on purpose:

  • Pinning. Ladder rungs 4 and 5 break clients that pin public CAs or use mTLS client certificates. There is an operator-only escape valve (HERDER_PROXY_PASS_THROUGH) that falls back to a plain tunnel when MITM setup fails — but the default stays fail-closed, because a capture that silently stops capturing is worse than an error.
  • Read-after-exfiltration. Every rung still assumes the agent has the workspace. Egress control narrows reach; it is not a full data-DLP product — though lock-inspect sample rules can alert or block on secret-shaped bodies, and captures are redacted by default (full plaintext retention is the customer's compliance call).

Cwd jail, per-den caps, and the deny ACL live beside this in the dashboard: per-den Deny / Block / Redirect rules and reusable rule sets on the Egress page.

DNS steal (host :8853)

On host Docker, Podman, and Swarm, every lock* den has its UDP and TCP :53 stolen: per-bridge PREROUTING NAT REDIRECT to herder serve on :8853. The laptop's resolver and systemd-resolved stay on :53. dig @8.8.8.8 from a locked den still lands on Herder.

Den Stolen? Logged? Unknown qname
lock* yes allow and deny NXDOMAIN (rcode 3; no upstream)
open (default) no no real resolver (8.8.8.8 / Docker DNS)
open + den/floorplan log_dns or org log_open_dns yes yes forward (not fail-closed)

Allowed A/AAAA names go to HERDER_DNS_UPSTREAM (else non-loopback system DNS, else 1.1.1.1). Unparsable queries are never forwarded. In lock, and for any blocked name, TXT/ANY/HTTPS/MX and other non-A/AAAA types are NXDOMAIN and never look upstream. PTR reverse lookups still forward. Mongo rows include stolen_dest when the kernel exposes the original destination (so you can see the den asked 8.8.8.8).

Where to read it. Anyone who can manage a den: den detail DNS and Proxy accordions (GET /api/v1/dens/{id}/dns-events, …/proxy-events). Org admins and super-admins also get Network (GET /api/v1/dns-events hunt; owners get 403). Proxy CONNECT is a separate collection — lock-audit+ only; lock / open say “use DNS.”

iptables still does not log dropped TCP. Fail-closed REJECT on non-DNS egress is silent. You see lookups (and stolen dest) plus lock-audit CONNECT lines — not a packet log of every blocked :443.

Misbehaving dens

A den that floods its control socket, DNS, or the audit proxy is held: force-stopped, control socket removed, hold persisted on the record. The owner gets 409 on start/stop/restart/rebuild/transfer/terminate so they cannot wipe the den before an operator looks. Org admins and super-admins can Hold / Release hold from the dens list.

Thresholds live in Ops (host defaults, org overlay). Env vars (HERDER_CONTROL_RPS, HERDER_DNS_ABUSE_SUPPRESS, HERDER_PROXY_ABUSE_CONNS, HERDER_ABUSE_HOLD=1) seed the host document until an admin saves. The sidecar writes a flag under $HERDER_STATE_DIR/abuse; herder serve drains it. The socket handler also bounds concurrency, body size, and paths so a malicious den cannot thread-bomb the Herder process.

Cwd jail

In a container den, session create, workspace IO, and cwd typeahead stay under RACCOON_CWD. Agents can still exfiltrate workspace secrets; the uid split only protects the herder product tree.

Production edge
